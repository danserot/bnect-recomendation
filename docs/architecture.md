# Устройство прототипа

## Путь запроса

Текущий простой интерфейс показывает каталог. Нажатие на тендер открывает сведения и вызывает `GET /api/tenders/:id/similar` без профиля поставщика и дополнительных параметров. Backend строит query-вектор выбранного тендера, исключает его ID и возвращает до пяти ближайших закупок по всем регионам. Поиск по номеру/названию и регион каталога не ограничивают выдачу похожих закупок.

В основе также сохранены отдельные POST API для рекомендаций по поставщику, явных ограничений и PCA. Для этих API React-клиент может передать профиль и фильтры; Zod проверяет запрос. `EmbeddingProvider` строит запросный вектор; PostgreSQL отбирает допустимые записи и сортирует их по cosine distance. Сервис добавляет объяснения из исходных полей. В текущем простом интерфейсе эти дополнительные сценарии не отображаются.

Сценарий A использует текст специализации поставщика. Название компании не заменяет специализацию и не участвует в embedding. Сценарий B строит отдельный `query:`-вектор текста выбранного тендера, исключает его ID и явно использует те же включённые ограничения. Хранящийся `passage:`-вектор выбранного тендера не подставляется вместо query-представления E5.

Поиск каталога по номеру/названию — отдельный `ILIKE`-запрос; он не является векторной рекомендацией. Его региональный фильтр отделён от географии рекомендаций в интерфейсе.

## Хранение и совместимость

`tenders` хранит предмет закупки и структурированные поля. Уникальный номер обеспечивает upsert при импорте. Embedding хранится с ID модели, версией представления, SHA-256 смыслового текста и временем вычисления. Если изменились только регион, номер, дата, статус или способ закупки, смысловой текст остаётся прежним и embedding можно сохранить. Изменение title/description/отрасли/деятельности/вида закупки требует пересчёта соответствующей записи.

Версия представления включает заданную версию текста и revision модели. Несовместимые проиндексированные записи блокируют векторную выдачу до явной переиндексации. Отсутствие embeddings и недоступность модели/БД возвращаются как ошибки, без запасного фиктивного поиска. Проверка полноты/версии, подсчёт кандидатов, рейтинг и векторы для PCA читаются в одном `REPEATABLE READ READ ONLY`-снимке: параллельный импорт или переиндексация не меняют пространство посередине запроса.

Модель загружается лениво один раз на процесс. Вычисления выполняются пакетами с одной последовательной линией inference; это ограничивает потребление памяти. Запросные вектора кешируются ограниченным кешем. Кеш документов хранится в БД и проверяется по хешу и версии. Векторы: 384 компоненты, `q8` ONNX CPU, masked mean pooling в Transformers.js и L2-нормализация. Максимальная длина E5 — 512 токенов; длинные тексты обрезаются токенизатором, поэтому ключевые сведения должны находиться в начале.

## Косинусный поиск

\[ similarity(a,b) = \frac{a\cdot b}{\|a\|\|b\|} \]

В pgvector `<=>` — косинусное расстояние; сходство равно `1 - distance`. Регион не получает вес или бонус: он ограничивает кандидатов. При равных расстояниях ID задаёт устойчивый порядок. В прототипе нет HNSW/IVFFlat, выполняется точный поиск.

SQL ниже показывает используемую операцию. Репозиторий формирует только включённые предикаты и передаёт значения параметрами; полный выполняемый SQL находится в `backend/src/repository.ts`.

```sql
SELECT *, embedding <=> $3::vector AS distance
FROM tenders
WHERE embedding IS NOT NULL
  -- Ниже только включённые ограничения, до ORDER BY и LIMIT:
  AND region_id = ANY($1::text[])
  AND id <> $2
ORDER BY distance ASC, id ASC
LIMIT 5;
```

В режиме «Все регионы» регионального предиката нет. В режиме «Регионы поставщика» используются ID профиля; в режиме «Выбранные регионы» — явный список. Пустой список в ограниченном режиме — ошибка, а не весь Казахстан. Неизвестный регион (`null`) проходит только при отсутствии регионального ограничения. Алиасы разрешаются точным сравнением после нормализации, без поиска по подстроке.

По желанию включаются ограничения отрасли и вида закупки профиля, явные отрасль/вид/способ закупки и открытость на заданное `demoNow`. Пересекающиеся ограничения применяются совместно. Если кандидатов мало, ограничения сохраняются. Поля профиля без включённого ограничения описывают смысл запроса и наблюдаемые совпадения; не являются скрытым дополнительным фильтром.

## Объяснения

Порядок определяется полными embeddings. Наблюдаемые совпадения отрасли, деятельности и вида закупки показываются отдельно. Это детерминированные поясняющие признаки, а не разложение вклада слов в embedding. География, статус и дедлайн — ограничения. Неизвестные данные так и обозначаются. Нет генерации объяснений LLM и утверждений о лицензиях или квалификации.

## PCA

PCA обучается на центрированных passage-векторах тендеров. Две главные компоненты вычисляются детерминированным степенным методом с ортогонализацией и фиксированным знаком компонент. Запросный вектор центрируется тем же средним и проецируется на те же компоненты. Доля объяснённой дисперсии отражает информацию только в двух осях.

Преобразование кешируется по составу и версиям embeddings и не переобучается при переключении поставщика. Все рекомендации вычисляются в исходных 384 измерениях. Координаты графика не определяют рейтинг; близость в 2D может искажаться. Цвет обозначает отрасль, отдельный символ — запрос профиля, обводка — рекомендации/выбранный тендер, приглушение — отфильтрованные записи.

## Импорт и внешние источники

CSV-адаптер принимает UTF-8, разделители `;` или `,`, заголовки из README, корректные кавычки и многострочные ячейки. Даты: `ДД.ММ.ГГГГ`, `ГГГГ-ММ-ДД` или ISO с часовым поясом; невозможные календарные даты отклоняются. Дополнительные столбцы `Описание`, `Статус`, `Срок подачи заявок` необязательны. Значения не достраиваются. Повтор номера внутри файла отмечается в отчёте; последняя корректная строка этого номера имеет приоритет. Ошибки строк не скрываются.

Если хотя бы одна строка содержит ошибку, CLI отменяет весь импорт. Dry-run с корректными строками показывает предполагаемые вставки/обновления и выполняет rollback. На PowerShell, где npm может забрать `--dry-run` как свой флаг, CLI также учитывает переданный npm `npm_config_dry_run`.

`SupplierSourceAdapter` отделяет поставщиков от тендеров. Реализован адаптер demo-профилей в локальной БД. Подключение существующего источника требует явно сопоставить его реальные поля с `SupplierProfile`; схема внешней БД не предполагается. Для переноса достаточно адаптировать получение тендеров и профилей, сохранить построение текстов и условия поиска, затем отдельно переиндексировать реальные данные.

## Большие объёмы

HNSW можно добавить после измерения задержки и качества на репрезентативных данных:

```sql
CREATE INDEX CONCURRENTLY tenders_embedding_hnsw
ON tenders USING hnsw (embedding vector_cosine_ops);
```

Это изменение переводит поиск в approximate-режим. В отличие от точного перебора, с HNSW фильтрация может применяться после обхода индекса, поэтому top-k может содержать меньше допустимых результатов и иметь меньший recall. Нужны измерения относительно точного поиска, настройка `hnsw.ef_search`, iterative scans pgvector 0.8+, оценка частичных индексов/partitioning по реальной селективности. Дополнительный стабильный порядок по ID также влияет на план — необходимо проверять `EXPLAIN (ANALYZE, BUFFERS)`. Нельзя обещать время ответа или полноту на больших данных без таких замеров.

Для текущих 96 demo-записей точный поиск проще проверять. Очереди, Redis и отдельные сервисы не нужны. Долгое первое вычисление связано с загрузкой модели и индексацией; UI показывает реальное ожидание/ошибку и не придумывает процент завершения.

Официальные источники: [модель ONNX](https://huggingface.co/Xenova/multilingual-e5-small), [E5: pooling, префиксы и ограничения](https://huggingface.co/intfloat/multilingual-e5-small/blob/main/README.md), [Transformers.js 3.8.1](https://huggingface.co/docs/transformers.js/v3.8.1/api/pipelines), [pgvector: операторы, фильтрация и HNSW](https://github.com/pgvector/pgvector).
